DOMS explained

How the deterministically optimal minesweeper solver in wasm/src/doms finds the fewest clicks, which minesweeper facts it already uses, and which it doesn't use yet.

The boards, numbers, optimal solutions and example DP states are all computed in the page by doms-model.js, a small JavaScript copy of the DOMS model. Nothing is typed in by hand, so every number on every board matches its mines. The toy DP has merging and pass-1 dominance but not passes 2 and 3 or the comparison caps. The self-check at the bottom compares it against brute force.

1. How the algorithm works

1.1 The problem

DOMS knows where every mine is and wants the shortest click sequence that clears the board. Only three kinds of click exist: left click, right click (flag), and chord (clicking a revealed number whose flags are all placed, which opens all its other neighbours). The yardstick is 3BV: every opening (a connected zero region plus the numbers around it) and every island (a number not touching any zero) needs one left click if you never chord.

1.2 What a chord does

Every numbered safe cell is a chord candidate. For each candidate c DOMS precomputes three sets, and after that it never needs to look at the board again:

  • M(c): the mines that must be flagged before chording c.
  • B(c): the 3BV units the chord solves (openings it floods, adjacent islands, and c itself if c is an island).
  • N(c): the other candidates the chord reveals, either directly or through an opening it floods. Revealed candidates can be chorded next without another left click.

1.3 The objective

A solution is just a set S of cells to chord. Everything else follows from S: flag every mine next to S, give each connected group of chords (a chain) one starting left click, chord the chain in reveal order, then left-click whatever 3BV is still unrevealed.

clicks(S) = |S| chords + |mines next to S| flags + (number of chains) seed clicks + (3BV units no chord in S solves) left clicks

1.4 Checking the answer

The click list can be replayed on a real board. DOMS does this after every solve, and so does this page.

1.5 Why a sweep

Trying every S is hopeless. Instead DOMS puts the candidates in a fixed order and decides "chord or not" for one candidate at a time. The key fact is that a chord only affects its 8 neighbours (plus any opening it floods). So once the sweep has moved on, most of the past can be forgotten.

1.6 The frontier state

After deciding some prefix of the order, only two kinds of thing still link the decided cells to the undecided ones:

  • Unfinished chains, each recorded as the set of undecided candidates it can still reveal. If one of those is chorded later it joins the chain for free. If the set runs out, the chain is finished and its seed click is charged.
  • Active factors: mines and 3BV units with neighbouring candidates on both sides of the sweep. For each, one bit says whether it has already been flagged or solved.

That pair (chains, factor bits) is the DP state. Its cost is the number of clicks committed so far.

1.7 One decision

Each state produces two children. The cost bookkeeping starts at 3BV (every unit left-clicked) and adjusts as decisions are made: +1 per chord, +1 the first time each mine is needed, −1 the first time each 3BV unit is solved, and +1 when a chain can no longer grow. When everything is decided the total is exactly clicks(S).

Not every state needs both children. A few cheap tests can prove that chording the candidate can never beat leaving it out, and then only the skip child is built (3.10 and 3.11).

1.8 Merging identical states

The states are kept in a hash table keyed on (chains, factor bits). When two histories arrive at the same key, only the cheaper one is kept. This alone turns an exponential number of histories into a number of states that grows with the width of the frontier, not the size of the board.

1.9 Dominance, pass 1: same chains, different bits

Two states with the same chains but different factor bits can still be compared. The cheaper state A can only lose its lead through bits where B is "ahead": a mine B has flagged but A hasn't, or a 3BV unit A has solved but B hasn't. Each of those is worth at most one click of future difference. If A's lead is at least that count, B can never win and is deleted.

1.10 Dominance, pass 2: coarser chains

States can also differ in their chains. Merging chains together never costs more future seed clicks, so a state whose chains are a coarser grouping of the same future reach can dominate a finer one using the same factor test. prune.rs buckets signatures by their total reach and uses a matching test (Kuhn's algorithm) so that no coarse chain ends up needing a seed the fine state wouldn't pay.

1.10a How pass 2 stays cheap

Pass 2 is more powerful than comparing only identical chains, but it cannot afford to compare every pair of states. It therefore rejects most impossible pairs before running the exact coarsening test. States are sorted by (cost + 3BV hits, cost, −total hits); a possible dominator must occur no later than its target in that order, so the scan only looks backwards. A cached quasi-score, cost + 3BV hits − mine hits, rejects pairs whose factor costs already make domination impossible.

The remaining candidates are narrowed again. Signatures are grouped by the exact set of future cells they can reach, because a coarsening cannot change that set. A coarse signature must have no more chains than the fine one, and its sorted chain reach sizes must be large enough to pair with the fine sizes. Only then does prune.rs run the matching test that checks whether every fine chain is covered by a distinct coarse chain. These are cheap necessary conditions; the final matching test is still the exact proof.

1.10b Dominance, pass 3: finer chains dominating coarser

Pass 2 only lets a state with coarser chains remove one with finer chains. The reverse can be sound too, when the finer state is far enough ahead. Picture a chain that wanders through the already-decided region and pokes out at the top and the bottom of the frontier. Only a chain with the same shape, but broader, could dominate it in pass 2. A state whose chains poke out in the same two places as separate pieces, without the costly path between them, is often much cheaper, and that lead can be enough to remove the wandering one.

The catch is seeds. Every unfinished chain costs one seed click when it finishes, unless a later chord joins it to something. The coarse state B has already been joined; the fine state A might never be. In the worst case the future never links A's extra pieces, so A pays one more seed for each extra chain. That number is the charge, and it is the most A can lose. A dominates B when the lead covers the factor penalty and the charge:

cost(B) − cost(A) ≥ factor penalty(A, B) + (chains of A − chains of B)

The factor penalty is the same one passes 1 and 2 use.

The chains have to split exactly. A charge of one seed per extra chain only holds when B's chains are exactly A's chains grouped together: each of A's chains lies inside exactly one of B's chains, and each of B's chains is exactly the union of the A chains inside it. Then any later chord that touches a B chain also touches one of its pieces, so every link the future makes between B's chains also links their pieces in A. A can only be behind by the pieces within one B chain that the future leaves apart.

This is not pass 2's test run backwards. Containment plus a matching is not enough when chains overlap, and the table below shows two overlapping cases where A really could lose more than the charge. An A chain that fits inside two B chains is rejected too, because the future could attach it to either. Rejecting a pair is always safe: the state is just left alone.

Why it can't delete everything. Pass 2 lets states it has already removed keep acting as dominators until the scan finishes, which is safe because every pass 2 edge goes from a state with fewer chains to one with more. Pass 3 adds edges the other way. Each needs a cost lead of at least its charge, which is at least 1. Going around a loop of dominations, the cost leads must add up to zero, so no loop can contain a pass 3 edge. Every removed state therefore still has a surviving state that is at least as good, and the optimum stays exact.

Keeping it cheap. Pass 3 runs after pass 2 and reuses its data: the buckets of equal total reach, the signatures grouped by chain count (now scanned for more chains instead of fewer), the sorted chain reach sizes, and the quasi-scores. The targets are the pass 1 survivors that pass 2 did not remove. The filters are pass 2's turned around, each with the charge included:

filterwhat it proves
same bucketan exact split has the same total reach on both sides
strictly more chainswith equal counts an exact split is the same signature, which pass 1 already handled
sort keythe dominator's cost + 3BV hits plus its charge cannot exceed the target's, so the scan can stop early
quasi-scorethe factor bound plus the charge already exceeds the cost lead

Pass 3 has its own budget of 500,000 comparisons per layer, separate from the 10,000,000 of passes 1 and 2 (1.14). It can neither use up their budget nor be starved by it. Like theirs, it only affects how many states survive, never the answer.

1.12 Choosing the sweep order

The number of states grows roughly exponentially with the cut width: the number of chains that could still grow plus the number of active factors. order.rs estimates the width of rows, columns, bands of several lines and a "smart" best order within each line, and picks the narrowest. On expert boards columns (16 tall) usually beat rows (30 wide). Section 4 explains how.

1.13 Rebuilding the clicks

Every state carries a bitset of its chords. The final state (no chains, no active bits) holds an optimal S. solution.rs re-evaluates S from scratch, checks the cost matches the DP, orders each chain's chords breadth-first from a seed, and replays the clicks on the board.

1.14 State limit and comparison cap

Two different limits protect the solver from spending unbounded time or memory. The normal defaults are a maximum of 2,000,000 live states in one layer and a budget of 10,000,000 state-to-state dominance comparisons in one pruning pass. They control resources, not the mathematical objective.

The state limit is a hard stop. After a layer has been merged and pruned, if too many states remain, DOMS returns a state-limit error with the layer where it happened. It does not choose the best state seen so far and call that an answer, because that could discard the true optimum.

The comparison cap is different. Every comparison it does make uses the same sound dominance proof described above. When the budget runs out, the solver simply stops attempting more comparisons and keeps the states it has not checked. That can leave more states for later layers and make the solve slower or reach the state limit sooner, but it cannot remove a state that might be better. A completed solve therefore remains exact; the cap limits pruning work, not answer quality.

Pass 3 (1.10b) has its own separate budget, so it cannot use up the one for passes 1 and 2. It too only affects how many states survive.

1.15 Transition caching

A state has two conceptually separate parts: its connectivity signature, meaning the unfinished chains and the cells each chain can still reveal, and its factor bits, meaning which mines and 3BV units have already been paid for. The same signature often appears in many states with different factor bits and costs.

ConnectivityPool interns each distinct, sorted chain signature once and gives it a small integer id. In a frontier layer, frontier.rs computes the two chain-only transitions for each old signature id: what happens if the next candidate is skipped, and what happens if it is chorded. It caches those results and reuses them for every state with that signature. Each state still applies its own factor-bit changes, cost delta, and dominance rules, so caching shares only the connectivity work that is genuinely identical.

This is why a state stores a signature id plus factor bits instead of copying every chain bitset. Interning saves memory, while the per-layer transition table avoids repeating the same chain update once for every state that happens to share it.

2. The minesweeper ideas DOMS already uses

Most of DOMS's speed comes from turning minesweeper facts into things the DP can forget or merge. These are the ones already in the code.

2.1 3BV units are the only thing a left click buys

Border numbers are not 3BV in their own right; they come free with their opening. So the model only tracks openings and islands. An island counts as solved by its own chord, because a chorded island is either revealed by a neighbouring chord or is the chain's seed. Either way its own left click is already paid for.

2.2 Openings are hubs

Flooding an opening reveals all its border numbers at once. So every border of an opening "reveals" every other border, and all chorded borders of one opening are always in the same chain. This is what lets two chords on opposite sides of a big opening share a single seed click.

2.3 A mine only matters while its neighbours are being decided

A flag is needed exactly when one of the mine's numbered neighbours is chorded. Before the sweep reaches the first neighbour the mine can't have been flagged. After the last neighbour its cost is settled. So the "flagged yet?" bit only exists in between. 3BV units work the same way. This is the biggest reason the state stays small.

2.4 Flags already placed and 3BV already solved

Pass-1 dominance is the minesweeper intuition "a flag you've already placed is a discount on the future, and a 3BV you've already solved is a discount you've used up":

2.5 Chords are local, so the frontier is thin

With king-move adjacency, a decided cell stops mattering once its neighbours are decided. The live part of the past is a strip about two cells deep along the sweep line. That's why sweeping the shorter dimension wins and why bands of lines are sometimes better.

3. Applied and possible improvements

This section started as a list of ideas the original frontier DP did not express. Several are now implemented. Each subsection says whether it is applied in the Rust solver or remains a possible improvement; the numbering stays stable so links and discussion remain easy to follow.

3.1 The blind spot: exchanges (applied dynamically)

DOMS's dominance only ever says "A is no worse than B if both make exactly the same future chords". It can't express the most natural minesweeper argument: "whatever you did with chord c, chord d instead". Two histories that differ in c vs d usually have different chains and different bits, so neither ordinary dominance pass compares them. The frontier solver now handles a bounded version of this argument while building each layer: if a later partner covers the relevant reveals and factor differences are already paid, the chorded child is skipped.

The runtime version of this argument is described in 3.11.

3.2 Rule A: the swap rule (applied statically, exact)

Remove candidate c before the DP runs if some other remaining candidate d satisfies all three of:

  1. M(d) ⊆ M(c): d never needs a flag c doesn't,
  2. B(c) ⊆ B(d): d solves every 3BV unit c does,
  3. N(c) \ {d} ⊆ N(d): d reveals every candidate c does.
Why this is exact

Take any solution S that chords c. If S also chords d, drop c: flags can only go down, B(c) is still solved by d, and anything connected through c is connected through d. If S doesn't chord d, swap c for d. Whatever revealed c is in N(c) \ {d}, so it also reveals d (if c was a seed, seed d). The swap has the same chord count, a subset of the flags, a superset of the 3BV solved and a superset of the connections. Either way the result is no worse. Applying the rule repeatedly is fine as long as each removal uses a d that is still present.

3.2a The strong swap rule (applied statically, exact)

Rule A asks d to be at least as good as c on every count. Often d is better overall without being better on each one: d needs a flag c doesn't but solves a unit c doesn't, or c has mines of its own that more than pay for the neighbours d can't reveal. The strong swap rule balances the two sides. Anything both chords share cancels, so only what is on one side matters:

setmeaningeffect of swapping c for d
Mc = M(c) ∖ M(d)mines only c needssaves those flags
Md = M(d) ∖ M(c)mines only d needscosts those flags
Bc = B(c) ∖ B(d)units only c solveseach needs a left click again
Bd = B(d) ∖ B(c)units only d solvessaves those left clicks
X = N(c) ∖ (N(d) ∪ {d})chords c reveals that d doesn'tmay leave a piece of c's chain without a seed

Rule A is the case where Md, Bc and X are all empty. The new rule instead works out the worst case over every other chord R in a solution that contains c:

  • d is not chorded. Chord d instead of c. The clicks change by at most
    |I| + |Md not flagged by R| + |Bc not solved by R| − |Mc not flagged by R| − |Bd not solved by R|
    where I has one chord from each piece of c's chain that d can't join, so I is a set of chords in X that don't reveal each other. This must be ≤ 0.
  • d is already chorded. Just drop c. d already pays for everything the two share, and already solves Bd, so no credit is given for it. The clicks change by at most
    −1 + |I| + |Bc not solved by R| − |Mc not flagged by R|
    which must also be ≤ 0.

Both cases are needed. A unit only d solves is only a gain when d is swapped in. If d was already chorded, that unit was already solved, so crediting it there would wrongly hide the cost of c's own units. Rule C is the same check with "swap c for nothing": budget 2 instead of 0 or 1, and I drawn from all of N(c).

Witnesses. A mine that some other kept chord also flags isn't a guaranteed saving, and a unit that some other chord also solves isn't a guaranteed gain. As in Rule C with witnesses, the worst case may include other chords of S. Any kept chord other than c and d that flags a mine of Mc or solves a unit of Bd is a witness. A free witness covers none of the costs that are still open, so the worst case always includes it. A costly witness also covers a cost (a mine of Md or a unit of Bc), and only helps the worst case when it covers more savings than costs. Two limits apply: a witness can't touch two members of I, and a witness that d reveals can't touch any of them, because that would put the member in d's piece instead of its own. Unlike Rule C there is no special case for I empty, since c's neighbours can belong to d's piece.

Why this is exact

Chords, flags and units that c and d share are in S before and after, so they cancel. Of c's chain pieces after c is removed, the ones that touch N(d) join d (or, if d was already chorded, are already part of its piece), so only the pieces with no chord in N(d) can need a new seed. Each such piece has a chord next to c, which is in X, and chords from different pieces don't reveal each other, so one from each forms an independent set I. The flags and units are counted against what the remaining chords R cover, and R is I together with some set of witnesses that respects the two limits. The check covers every I and every such set, so it covers every solution.

The Rust check runs after the witness rule has settled and only on the candidates it kept. For each c it looks at the chords that share a mine or a unit with c or are revealed by it. Two checks that only compare counts, |Bc| ≤ 1 + |Mc| and |Md| + |Bc| ≤ |Mc| + |Bd|, throw out most pairs before any search. Each candidate gets at most 20,000 search steps in total across all its partners and both cases; running out just keeps the candidate, so only reduction is lost, never correctness. The witness rule runs again whenever the strong swap removes something.

In the first board d can't reveal one of c's neighbours and c solves a unit d doesn't, but c's two private mines pay for both. In the second, d's extra mine is paid for by an island only d solves.

3.3 Rule C: left-click-equivalent chords (applied statically, exact)

Sometimes chording c is worth no more than a couple of ordinary clicks nearby. Rule C removes c when every solution that chords it can drop that chord without costing any extra clicks.

Take a solution S that chords c, and remove c from it. Let I hold one chord from each piece c's chain splits into, so I is a set of chords next to c that don't reveal each other (I is empty if c was alone). The number of clicks changes by

|I| − 2 − saved + lost

  • −2 is the chord on c and the seed click of its old chain, and +|I| is one new seed for each piece the chain splits into.
  • saved is the number of flags that only c needed.
  • lost is the number of 3BV units in B(c) that no remaining chord solves, each now needing a left click.

Rule C removes c if this is never positive, so |I| + lost ≤ 2 + saved. It can't know what the rest of S looks like, so it takes the safe bound for each side. lost is at most the number of units of B(c) that I doesn't solve, and saved is at least private(c), the number of mines of c that no other kept candidate needs. Remove c when, for every set I of kept candidates in N(c) that don't reveal each other (including the empty set):

|I| + |B(c) not solved by I| ≤ 2 + private(c)

Why this is exact

Whatever S is, c's chain splits into some number of pieces after c is removed, and one chord from each piece forms an I of the kind the rule checks. Units lost are never more than the ones I fails to solve, and the flags only c needed are saved no matter what else S contains. So the real cost change is never worse than the bound for that I, and checking every I covers every possible S without depending on how S got to c.

An earlier version of this idea, Rule B, allowed only two lost 3BV units and at most two chain pieces. It is a weaker special case of Rule C, so it no longer exists as a separate rule.

3.3a Rule C with witnesses (applied statically, exact)

Rule C's credit for flags is very cautious. A mine of c that some other kept candidate also needs gives no credit at all, on the assumption that the other candidate is chorded anyway and flags it for free. Call a kept candidate d ≠ c that needs one of c's mines a witness for c. Two things make that assumption too pessimistic:

  • A witness can cost the adversary a unit. If d also solves a unit of B(c), then having d in S removes one saved flag but also one lost unit, since d solves that unit whether or not c is dropped. The two cancel, so d is no help in making dropping c look bad. This is the common case.
  • Not every witness can be in the same solution as I. A witness touching two members of I would put them in the same piece of the chain, which contradicts I having one member per piece. This is rare. When I is empty, c is alone, so a witness next to c can't be chorded either, but that case never changes the verdict, because such a witness could instead be put in I. Rust skips them anyway, since it saves search.

For a fixed I, write U for the units of B(c) that no member of I solves and F for the mines of c that no member of I needs, since members of I pay for their own flags and solve their own units. Each usable witness has the mines of F it flags and the units of U it solves. Witnesses that solve no unit of U are free: they flag mines at no cost, so the worst case always includes them. Witnesses that do solve a unit of U are costly: the worst case only includes a set of them if they flag more new mines than the units they solve. For a set D of usable witnesses the change in clicks is at most zero when:

|I| + |U not solved by D| ≤ 2 + |F not flagged by D|

Rule C with witnesses removes c when this holds for every set I of kept candidates in N(c) that don't reveal each other, whichever set D of witnesses is used. Rule C is the special case where witnesses cost nothing and every one of them is usable, so anything Rule C removes this rule removes too.

Why this is exact

Again take any S containing c, with I the representatives of c's pieces. Every chord of S other than c and I either touches no mine or unit of c, which only helps, or is a witness, and a witness in S can't touch two members of I. So the flags actually saved and the units actually lost are those of a usable set D, which is what the check ranges over. The check also treats chains that merge indirectly as separate, which can only make it stricter. If it passes, the real change in clicks is at most zero for every S.

The Rust check runs after the cheaper rules have reached a fixpoint, so it only looks at the candidates they couldn't remove. For each I it takes the free witnesses at once, discards costly witnesses that another one beats (more mines, no more units) and searches the rest with a bound. It stops at the first failing I. Each candidate gets at most 20,000 search steps; running out just keeps the candidate, so only reduction is lost, never correctness. Large openings are the case where many sets I exist, since any one border can be a member.

3.4 How much the static rules remove (applied before the frontier DP)

Before choosing a sweep order, Rust repeatedly applies the swap rule and Rule C to the currently kept candidates, then repeats with Rule C with witnesses added, and finally with the strong swap rule added (the default). Removing a candidate means one fewer branching decision. It also shortens the window of every mine and 3BV unit next to it, and drops the candidate from every chain reach set, so more states become identical and merge. The reduced model filters candidate-related lists before solve_frontier; brute force tests still use the unreduced model to verify that the optimum is unchanged. The explorer below starts with this fixpoint reduction, while its targeted buttons demonstrate one snapshot pass at a time. A snapshot evaluates every candidate using knowledge from the beginning of the pass, then removes the safe batch together. Rule C and Rule C with witnesses remain safe when batched because removing candidates only shrinks the sets they quantify over, so their conditions only get easier; a swap batch (either swap rule) additionally preserves each removal's partner, so two mutually dominating candidates cannot remove each other. A targeted pass briefly highlights its newly removed cells with a yellow-to-grey background transition, which can be disabled with the checkbox; clear restores all candidates without changing the board. Teal crosses are the candidates only Rule C with witnesses removes, and orange crosses the ones only the strong swap removes.

3.5 Opening-chain absorption (applied, exact state equivalence)

Once the sweep has passed every chord in a chain except its link into an opening, the chain can only grow through that opening's remaining borders. That state is exactly equivalent to a state with no chain, the opening unsolved, and one extra click. In minesweeper terms, "the opening is open" is worth exactly one click, the same as clicking it.

The frontier transition now applies this equivalence locally: after a transition, if an opening factor is hit and a chain's reach equals that opening's undecided borders, it deletes the chain, clears the opening bit and adds one click. 3.6 Factor cancellation (applied dynamically, exact)

Pass 1 treats every "red" bit as a click the future can win back for free. But sometimes the only undecided candidates that can trigger a red bit are all among those that trigger a "green" bit. Then the future can't collect the red one without also collecting the green one, and the two cancel. A common case is a mine just behind the sweep next to an island just ahead of it: every remaining chord that needs that flag also opens the island. The containment only depends on the layer, so it is precomputed per candidate. The frontier solver uses a matching of red to green bits as a tighter bound before deciding whether the chorded child needs to be built.

The same red/green matching is used inside the forced-skip bound (3.10b), which is where it is applied in the Rust solver today. The pruning version shown here is not in the Rust solver.

3.7 Coarser chains with more reach

Pass 2 only compares signatures with the same total reach. But a chain that can reach more undecided cells is never worse, because extra reach only means more chords that don't need a seed. The most common missed pair is "chord c, extending a chain" vs "skip c". Caveat: the cells c newly solves are usually still active, so the factor penalty often eats the lead unless cancellation (3.6) is also in. A cheap version would only test this sibling pair at transition time, where the bits are already computed.

The sibling-only version of this idea (chord c against not chording c, which was called forced chord) was tried and removed; see 3.13.

3.8 Chains that can only cost a seed

Suppose every pair of cells in a chain's remaining reach reveal each other: one cell, two adjacent cells, or any set of borders of one opening. Then the chain can join at most one future component. It can never save a seed click, only cost one. So a state without that chain is never worse than the same state with it. The current matching requires every fine chain to be covered, so this case is never used. Most chains only reach this condition in their last layer or two, so the gain is probably modest.

3.9 Seed slack: the general form

Pass 3 implements the simplest special case. The chains are an exact split, so only the "+1 per extra A chain" charge is left and no B chain is uncovered. The general form below also tolerates B chains that no A chain covers, which needs comparisons between signatures with different total reach. The buckets cannot index those, so that part is not implemented.

The sibling-only form of the α charge is used by the forced-skip rule (3.10).

3.10 Forced skip: the chord child that can never win (applied dynamically, exact)

When the DP decides candidate c it turns each parent state into two children, "skip c" and "chord c". Often the parent already contains enough information to prove that chording c cannot beat skipping it, whatever the rest of the solution looks like. Then the chord child is simply not built. This is different from dominance (1.9 to 1.10b): dominance compares two states that already exist, while this rule looks at one parent and decides which of its children to create. It is also different from the static rules (3.2 to 3.3), which have to hold for every history, whereas this one can use what this particular state has already paid.

The bound

Take any set F of later chords, and compare the best finish that chords c as well as F against the one that chords only F. Using the cost accounting of 1.7, the difference is the sum of four things:

  • +1 for the chord click.
  • Mines. c needs some flags. Those already placed cost nothing more. Of the rest, F might flag some, but a mine that no later candidate can flag (a private mine) must be paid for by c. So at least private extra flags.
  • Units. Chording c solves units, each saving a left click. The most it can save is every unit of c that is not yet solved in this state, so subtract unhit units.
  • Chains. Seeds are paid once per connected group of chords (1.3). Adding c starts a new group, +1, but it also joins every group it touches: the chains that can still reach c, and the groups of later chords that c reveals. So the group count changes by at least 1 − (chains + α).

slack = 2 + private − unhit units − chains − α

The 2 is the chord click plus the new group c would start. If slack ≥ 0, chording c never saves clicks compared to skipping it, for every possible F, so the chord child is dropped.

α is the number of components of later chords that c could touch. Two later candidates that reveal each other end up in the same group, so only candidates that do not reveal each other can be separate groups. α is therefore the size of the largest set of c's later reveals in which no two reveal each other (found by a small search, at most 24 reveals; above that α is just the number of reveals).

3.10a α from this state's chains

The α above is the same for every state, so it has to assume that every later reveal of c might be a separate group. A particular state knows more. If a later reveal of c lies inside the reach of a chain that can already reach c, then chording it in the future joins that chain whether or not c is chorded. That chain is already counted in the chains term, so the reveal cannot be an extra separate group. The solver therefore removes those reveals before looking for the largest independent set, giving a smaller α and a larger slack. The result is computed once per connectivity signature, so every state with the same chains shares it.

3.10b Cancelling a mine against a unit

The bound lets the future flag all of c's non-private mines for free and also solve all of c's units. Those two assumptions can contradict each other. Suppose a mine of c is flagged only by later candidates that also solve one of c's units. If the future flags that mine for free, it also solves that unit, so the unit cannot be counted as gained by c. Putting the pair together, the pair is worth at least 0 to the chord, not the −1 the plain bound used.

So before giving up, the solver matches each unhit mine of c to a distinct unhit unit of c, for mines and units that are still active after c (a factor c is the last candidate to touch is already settled), where every later candidate that can flag the mine also solves the unit. If the number of matched pairs is at least −slack, the chord child is dropped. This is the matching of 3.6, but applied to the two factors of one candidate inside the bound, not to two states. The matching is greedy, so it can miss a pairing a better matching would find; that only costs speed.

Why this is exact

For every F, the chord-minus-skip cost difference is at least slack. Each term uses a bound that holds for every F: private mines are paid by c whatever F is, unhit units are the most c can solve, and the group count drops by at most the number of groups c touches. For the pairs, a mine is paid by c exactly when F does not flag it, and a unit is gained exactly when F does not solve it; because every candidate that flags the mine solves the unit, "F misses the unit" implies "F misses the mine", so the pair contributes at least 0 for every F. Different pairs use different factors, so they add. If the bound is ≥ 0, no completion that chords c is cheaper than the same completion without c, and that completion still belongs to the skip child, which is always built. The skip child is never dropped by this rule, so the optimum from the parent is unchanged.

Checking these rules costs a few popcounts per state and the matching only when the plain bound fails. In testing, adding the sibling rules (forced skip and exchange) cut the total time on the community expert boards by roughly 15%, although the saving is mostly children that pruning would have removed a moment later anyway, so peak state counts barely move.

3.11 Exchange: letting a later chord stand in for c (applied dynamically, exact)

The swap rule (3.2) removes c for good when some d does everything c does for no more flags. It has to hold for every history, so it only fires when d is better on every count. The exchange rule is its runtime version: it only needs d to be no worse given what this state has already paid for. When it holds, the chord child for c is dropped, because any finish that chords c can be turned into one that chords d instead (or, if d was chorded anyway, nothing instead of c) at no extra cost.

The partner d has to be a later candidate, so the replacement is still an open decision. The rule fires for a state when some partner d passes three conditions:

  1. d reveals what c reveals. Every later candidate that c reveals, apart from d itself, is also revealed by d. This does not depend on the state, so it is decided once while setting up.
  2. The chains that reach c reach d. Every chain in this state that can still reveal c can also reveal d. This depends on the state's chains and is computed once per connectivity signature.
  3. The factor differences are already paid. The mines d needs that c doesn't, and the units c solves that d doesn't, have all been hit already in this state. Then swapping adds no flag and loses no unit.

Condition 3 is what makes this a runtime rule. A mine of d that c doesn't need might not be flagged in some history, in which case swapping would cost a flag; in another history the same mine was already flagged by an earlier chord and the swap is free.

Why this is exact

Take any set S that chords c and any state it passes through. If d is also in S, drop c. Otherwise swap c for d. The chord count does not rise. Flags: any mine d adds is already flagged by an earlier chord (condition 3), and mines only c needed are no longer needed. Units: any unit that c solved and d does not was already solved by an earlier chord (condition 3), and units only d solves are extra gains. Seeds: a group that c joined is either an earlier chain that reaches c, which also reaches d (condition 2), or a later chord that c reveals, which d also reveals (condition 1), so d joins every group that c did and the group count cannot rise. So the new set costs no more, and it is a completion of the skip child, which is always built.

Partners are only searched within reveal distance 2 of c, at most 64 per candidate, and a partner is dropped up front if it needs a factor that no earlier candidate can have hit, since condition 3 could never hold. The solver tries forced skip first, then exchange; a state's chord child is dropped at most once, by the first rule that proves it.

Extensions that were tried and not kept

Two strengthenings of the exchange rule were implemented and tried, but are not in the solver. They were not kept for reasons that can no longer be remembered, but probably because the benchmarks were poor. Both appeared sound on paper.

  • Cancellation among the factor differences. Condition 3 requires every difference to be hit already. A cost of the swap (a mine only d needs, or a unit only c solves) that is not yet paid could instead be matched against a saving the swap also brings (a mine only c needs, or a unit only d solves), whenever every later candidate that gains the saving also gains the cost's factor. This is the pairing of 3.10b applied to the exchange.
  • Signature-specific reveal coverage. Condition 1 requires d to reveal everything c reveals. A later reveal of c that already lies inside the reach of a chain that reaches c stays attached to that chain through condition 2, so d would only need to reveal the rest. This is the same idea as 3.10a.

3.13 Ideas considered and rejected

idea why not
"always chord c" rules Only provable when a 3BV unit can be solved by c alone. That almost never happens at 20% density, since islands are solved by themselves and all their numbered neighbours.
forced chord: skip the skip child when chording c is never worse The mirror of forced skip (3.10): chording c can be proved no worse than skipping when 2 + (unhit mines of c) − chains − (units only c can still solve) ≤ 0. It was implemented and measured, and made no useful difference (community expert boards on one thread, about 55.9 s with every rule and 54.8 s without it). It is the sibling-only form of 3.7.
history-dependent "never chord both c and d" rules Forbidding arbitrary futures for arbitrary states breaks the "every identical future" assumption that dominance relies on. The implemented rules are static or prove a sibling child is no better for the current state.
bound pruning (greedy ZiNi as an upper bound plus a lower bound per state) The upper bound exists (calculate_zini_8way), but cheap per-state lower bounds are off by tens of clicks, so they would prune very little.
merging mines whose neighbouring candidates are identical Their bits are always equal anyway, so this saves memory, not states.
splitting the board into independent regions At normal densities the mine/3BV/reveal interactions connect essentially the whole board.
"never chord an 8" style rules Too rare to matter, and the DP already discards them almost immediately.
capping the charge in pass 3 (for example only charge 1) Nearly all removals have charge 1, but the rare charge 2 ones each cut off a whole line of descendants. Allowing only charge 1 left 36% more states on the evil board and ran about 1.7 times slower. Allowing 2 changed nothing measurable, and pass 3 is only 6–9% of the solve time anyway.

4. Choosing the sweep order

4.1 What the order changes

Any order gives the same optimal answer. The DP is exact whichever order it sweeps in, so the order only decides how many states it has to carry, and therefore how long it takes and whether it fits under the state limit. choose_sweep_order runs once, before the DP, and only looks at the board's structure. It never runs the DP to compare orders. It scores a handful of candidate orders, keeps the best, and relabels the candidates (ChordModel::reordered) so that step k of the DP decides candidate k. Scoring every option takes milliseconds, far less than the solve itself.

4.2 Measuring a cut

The estimate for an order is the width of every cut, meaning the point between decision k and decision k+1. It counts the same two kinds of thing that make up the DP state (1.6), but only structurally, without knowing what was chorded:

  • Connectivity width: decided candidates that still have an undecided neighbouring candidate (any of them could be in a chain that can still grow), plus openings with border candidates on both sides (a chain through the opening can still grow through its undecided borders).
  • Factor width: mines and 3BV units with candidates on both sides. These are exactly the active factors, so each is one bit of the state.

Every item is "live" from the first to the last position of its candidates, so cut_widths_for turns each item into an interval and counts how many intervals cover each cut, using a difference array (coverage). That makes scoring one order linear in the board size. An opening with borders on both sides counts twice: once as connectivity and once as a 3BV factor.

4.3 Scoring an order

Each order gets a WidthEstimate, and estimates are compared field by field, in this order:

field meaning why
max_total widest cut (connectivity + factors) The widest layer dominates both memory and time, and it's where the state limit is hit.
max_connectivity widest connectivity part Chain signatures are more expensive than factor bits: there can be many ways to group the same boundary into chains.
max_factors most active factors at once Next tie-break.
work sum of 2width over all cuts A rough total-work estimate: between two orders with the same peak, prefer the one that spends less time near it.

Any remaining tie goes to the alphabetically first name, so the choice is deterministic.

4.4 Plain rows and columns

The baseline is the plain sweep: column by column from top to bottom, or row by row from left to right. Its frontier is roughly one line long plus a one-cell step where the current line is half done (2.5), so the shorter dimension usually wins (1.12). Both are always scored, and the better of the two is the benchmark the other options have to beat.

4.5 Smart orders within a line

The smart order keeps the line-by-line sweep but chooses the order inside each line. Top to bottom is just one of the n! ways to go through a line of n candidates. Deciding some candidates first can close off mines and 3BV units left over from the previous line, and leaving others until last delays opening new ones.

The key fact is that while the sweep is inside a line, every earlier line is fully decided and every later line is untouched. So the width of a cut inside the line depends only on which subset of the line has been decided, not on the order it was decided in. That turns "best order of the line" into a shortest-path problem over subsets: start from the empty set, add one candidate at a time, and minimise the widest cut along the way. With n candidates that is 2n subsets instead of n! orders, and the path found has the smallest possible peak within that line. Ties are broken by the same fields as 4.3.

Computing the width of all 2n subsets is the fiddly part. crossing_counts sorts every mine, 3BV unit and opening by which other lines it touches, and records its candidates on this line as a bitmask m:

  • touching earlier and later lines: always on the frontier,
  • earlier lines only: on the frontier until all of m is decided,
  • later lines only: on the frontier as soon as any of m is decided,
  • this line only: on the frontier while m is partly decided.

Each case needs "how many sets have m ⊆ this subset" for every subset, which a subset-sum (zeta) transform computes for all 2n subsets at once in n·2n steps. The boundary candidates of earlier lines are handled the same way, and the candidates of the line itself are checked directly.

Because of the 2n, smart orders are only tried when lines are at most 20 cells long, and only for an orientation whose plain sweep is within 2 of the best. On expert boards that means smart columns but never smart rows.

4.6 Bands

A band treats b neighbouring lines as one thick line. The sweep walks along the band, taking its b cells across at each step, then moves on to the next band. order.rs tries bands of 2, 4, 8, … lines and one band of the full board size, in both orientations.

Geometrically, bands should lose. The frontier of a band sweep runs along the previous band's edge, the band's own far edge, and a cross-section b cells long, which is about one line plus b instead of one line plus one. But the widths count candidates and sets, not cells. Zeros, mines and big openings make the real frontier lumpy, and on some boards a band is narrower at the point where both plain sweeps are at their widest. This happens more often on intermediate boards than on expert boards. Bands are cheap to score, so they are always tried, but a band is only accepted if it is at least 2 narrower than the best plain sweep, so that noise in the estimate doesn't swap in a strange order. The full-size bands are the same as the plain sweeps in the other orientation, so they can never pass that test.

4.8 Other uses of the widths

Before the DP starts, frontier.rs sends the cut widths of the chosen order to the caller (the Plan progress event). The site's worker (doms-worker.js) fits log(states) ≈ a + b·width to the layers solved so far and uses the remaining widths to predict the time left. The solve also reports the chosen order's name, its widest connectivity (maxBoundary) and its most active factors (maxActiveFactors).
