2. THE CORE ARCHITECTURAL PROBLEM (read this first)
================================================================================
Everything is entangled through ~174 module-scoped reactive refs declared inside
<script setup>. Because Game/Board are defined *inside* the same <script setup>
block, they close over those refs directly (e.g. `boardWidth.value`,
`tileSizeSlider.value`, `noGuessing.value`). The Board class alone reads ~73
distinct `.value` refs by closure. The template reads the same refs directly and
calls `game.board.<method>` in ~40 places.

This closure coupling is the single reason the file has never been split:
  - You cannot move the Board class to its own .js file without giving it access
    to those refs.
  - You cannot cleanly extract template chunks into child components without
    giving those components access to the same refs.

GOOD NEWS: the codebase already has the solution pattern. Several classes are
already extracted and receive their reactive dependencies via a "refs object"
constructor argument:
  - ZiniExplore(board, refs)          -> uses this.refs.analyseAlgorithm.value
  - SkinManager({ boardSkin, ... })
  - EffShuffleManager({ minimumEff, boardWidth, ... }, { begEffOptions, ... })
So dependency-injection-of-refs is an established, working pattern here.

THE ENABLING REFACTOR (do this before large extractions):
  Move the ~174 shared refs out of <script setup> into one or more composables
  (e.g. src/composables/useSettings.js or several grouped ones). Each returns
  its refs. <script setup> then does `const settings = useSettings()` and the
  extracted Board class / child components import the same composable. Because
  useLocalStorage/ref/computed are just module-level reactive values, a
  composable that instantiates them once (module singleton) behaves identically
  to today, but is now importable from anywhere.

  This is mostly mechanical (cut/paste + prefix references), low logic-risk, but
  it touches a lot of lines, so do it in grouped batches and test between each.

3. RECOMMENDED STRATEGY & SEQUENCING
================================================================================
Work in order of increasing risk. Ship and test after each phase.

  Phase 0  Quick wins that need no state untangling (dev code, style, stubs).
  Phase 1  Extract shared refs into composables (the enabler).
  Phase 2  Extract the Board class (+ Game, BoardHistory) into class files.
  Phase 3  Split the Board class internally by responsibility (mixins/helpers).
  Phase 4  Extract template chunks into child components (needs Phase 1 done).

Phases 2 and 4 both depend on Phase 1. Phase 3 depends on Phase 2. Phase 0 is
independent and can be done immediately.

Rough size impact (very approximate lines removed from PlayPage.vue):
  Phase 0:  ~700 lines   (dev/testing + trivial)
  Phase 2:  ~5900 lines  (Board+Game+BoardHistory moved out)
  Phase 4:  ~1500–2000   (template components)
  => PlayPage.vue could realistically drop from 10.4k to ~2–3k lines.

PHASE 3 — SPLIT THE Board CLASS INTERNALLY (by responsibility)
--------------------------------------------------------------------------------
Even after Board.js exists, 5700 lines in one class is still a lot. Board's
methods cluster into cohesive groups. Split each group into a mixin/helper
module that operates on a Board instance. Two viable mechanics:
  (A) "Mixin" style: define methods in a separate file as plain functions that
      take `board` as first arg, then attach: `Object.assign(Board.prototype,
      require('./boardInput'))` — or import functions and call
      `boardInput.handleTouchStart(this, event)`.
  (B) Sub-object composition: e.g. `this.input = new BoardInput(this)`,
      `this.renderer = new BoardRenderer(this)`, `this.paint = new QuickPaint(this)`.
      Mirrors the existing `this.ziniExplore = new ZiniExplore(this, refs)` model,
      which is the most consistent with current code.

5. CROSS-CUTTING GOTCHAS / RISKS
================================================================================
- useTemplateRef DOM refs (main-canvas, game-container) CANNOT move into
  composables or class files; they must stay in the component that renders the
  DOM. Board must receive them by injection.
- Global singletons (skinManager, effShuffleManager, statsWorkerManager,
  benchmark, boardHistory, game) are created at the bottom of <script setup> and
  referenced by closure inside Board. After extraction, inject them into Board's
  constructor (they already follow the DI-of-refs pattern, so this is consistent).
- `var game` / `var effShuffleManager` are intentionally `var` to dodge
  temporal-dead-zone "access before init" errors due to circular-ish references.
  Preserve initialization order when moving instantiation around.
- Watchers/watchEffect (3835, 3842, 3988) and onMounted/onUnmounted (3438+) are
  lifecycle-bound and must stay in the component (or be returned from composables
  that are called within setup). Do not move raw watch() calls into plain class
  files where there is no active component instance — the Board constructor
  currently calls watch() (see ~4788); when moving Board out, that watch still
  works because it's created during setup via `new Game()` at setup time, but
  keep it created synchronously during setup so Vue registers it to the instance.
- The template calls `game.board.<method>` ~40 times. When template chunks move
  to child components, decide a convention: inject the `game`/`board` instance
  (provide/inject) OR emit events. Injection is less boilerplate given how many
  calls there are; emitting is cleaner but higher churn.
- `scoped` styles: moving markup to a child without moving its styles will break
  styling (scoped attribute won't match). Move each component's styles with it.
- After each extraction, grep the moved block for bare identifiers that are no
  longer in scope (missed refs/singletons) — this is the #1 source of runtime
  ReferenceErrors in this kind of refactor. Test the specific feature after each
  step; do not batch many extractions before testing.
