Context: Phase 1 is done. All shared refs/localStorage now live in
src/composables/useSettings.js as a MODULE SINGLETON with named exports.

================================================================================
0. HEADLINE DECISIONS (the short version)
================================================================================
- Board reads settings by IMPORTING them from useSettings, NOT via constructor
  args and NOT renamed to `settings.x`. Existing `boardWidth.value` etc. stay
  verbatim; they just become import references.
- The ONLY things Board's constructor must be given (they cannot be plain
  imports) are the component-owned bits:
      { mainCanvas, gameContainerDiv, route, router }
  Everything else is an import.
- The `w, h, mines, tileSize, variant` args currently passed in
  Game.initialise() are VESTIGIAL — the Board constructor is `constructor() {}`
  and ignores them (resetBoard reads the refs directly). Delete them.
- The singleton managers (skinManager / effShuffleManager / statsWorkerManager /
  benchmark / boardHistory) become singletons EXPORTED FROM THEIR OWN CLASS
  FILES (no singletons.js). Board imports them.
- Board currently references the `game` singleton internally in 5 spots. Convert
  those to `this.` so Board no longer depends on `game` (kills the Board<->game
  import cycle).
- $q inside Board becomes direct `quasar` imports (Dialog/Notify/copyToClipboard/
  exportFile/Dark). `$q.dialog(...)` -> `Dialog.create(...)`, `$q.notify(...)` ->
  `Notify.create(...)`, `$q.dark.isActive` -> `Dark.isActive`.
- `wasmAvailable` is currently a local ref in PlayPage but Board reads it. Move
  it into useSettings so both can import it.
- NEW SIDE EFFECT of the module-singleton refs: plain `ref()` values now KEEP
  their value when you navigate away from PlayPage and back (they used to reset
  because they lived in <script setup>). localStorage-backed refs are unchanged.
  See section 9 for the reset list.

2. NEW CONSTRUCTOR SHAPE
================================================================================
  class Board {
    constructor(deps) {
      this.mainCanvas = deps.mainCanvas;
      this.gameContainerDiv = deps.gameContainerDiv;
      this.route = deps.route;
      this.router = deps.router;
      ...existing field init...
      this.ziniExplore = new ZiniExplore(this, { ...analyse refs... });
      this.stopUrlWatch = watch([...], ...);   // capture stop handle (section 7)
      this.resetBoard(true);
    }
  }

Then inside Board, mechanically replace bare identifiers:
  mainCanvas.value        -> this.mainCanvas.value
  gameContainerDiv.value  -> this.gameContainerDiv.value
  route.<x>               -> this.route.<x>
  router.<x>              -> this.router.<x>
Also in resetTiles(): `new Tile(CONSTANTS.UNREVEALED, { mainCanvas }, skinManager)`
  -> `new Tile(CONSTANTS.UNREVEALED, { mainCanvas: this.mainCanvas }, skinManager)`

Game.initialise() becomes:
  initialise() {
    this.board = new Board({ mainCanvas, gameContainerDiv, route, router });
  }
(No w/h/mines/tileSize/variant — they were dead args.)

Per-manager notes (verified):
  skinManager (SkinManager.js)
    - constructor deps: { boardSkin, analyseHiddenStyle, replayShowHidden } (all in useSettings).
    - Used by Board AND by PlayPage (onMounted addCallbackWhenAllPriorityLoaded/
      addCallbackWhenSingleImageLoaded) AND by Tile. Same imported singleton for all.
    - Begins image loading eagerly; now starts at import time instead of mount.
      Harmless (PlayPage is a lazy route, so its chunk only loads when you visit).

  effShuffleManager (EffShuffleManager.js)
    - Constructor does NOT spawn workers (new Worker lives in reinitWorkers()), so
      eager module-level construction has no side effects. Safe.

  statsWorkerManager (StatsWorkerManager.js)
    - WARNING: its constructor DOES `new Worker(...)` eagerly. As a module
      singleton the worker spawns at import time (still only when PlayPage's chunk
      loads, so timing is nearly identical to today).

  benchmark (Benchmark.js)
    - `new Benchmark()`, no deps. Board does NOT use it (only the dev bulkrun*
      functions do). Leave it wherever the dev code ends up; not needed by Board.

  boardHistory (BoardHistory.js)
    - Empty stub; Board.saveGameIfRunning only console.logs and never touches it.
      Move to its own file or delete. Not a Board dependency.

  *** TEARDOWN CONSEQUENCE (important) ***
  PlayPage onUnmounted currently does:
        effShuffleManager.killAllWorkers();
        statsWorkerManager.killWorker();
  Today these managers are re-created fresh on every mount, so killing on unmount
  is fine. As APP-LIFETIME SINGLETONS, killing their workers on unmount would
  leave a DEAD worker when you navigate back to PlayPage.
  Choose one:
    (a) Preferred: stop killing on unmount. Replace with a pause/deactivate:
        effShuffleManager already has deactivateBackgroundGeneration() (the
        watchEffect re-activates it); statsWorkerManager's worker can just sit
        idle. Accept that the worker lives for the session.
    (b) Or: re-init on mount (statsWorkerManager gains a reinit/ensureWorker()
        called from onMounted; effShuffleManager.reinitWorkers() as needed).
    (c) Or: keep these two NON-singleton and inject them into Board instead
        (skinManager/benchmark/boardHistory can still be singletons). More DI,
        but preserves exact teardown semantics.
  Recommendation: (a). Simplest and matches "singletons live for the session".

7. THE CONSTRUCTOR `watch()` — lifecycle consideration
================================================================================
Board's constructor calls watch([() => route.params.variant, () => route.query], ...).
Board is constructed via game.initialise(), which PlayPage calls from a
skinManager image-load callback inside onMounted. Two points:
  - Keep construction happening during setup/mount so Vue binds the watcher to
    the component instance and auto-disposes it on unmount.
  - CAVEAT (pre-existing, not introduced here): that image-load callback may fire
    ASYNCHRONOUSLY (after images load), at which point getCurrentInstance() can be
    null and the watch would NOT auto-dispose -> a stale watcher on an old Board
    could survive navigation. To be safe, capture the stop handle:
        this.stopUrlWatch = watch(...);
    and call this.stopUrlWatch() from a Board teardown method invoked in
    game.unmount() (onUnmounted). Low effort, closes a latent leak.

9. useSettings PERSISTENCE BEHAVIOUR CHANGE + REF-RESET LIST
================================================================================
WHY: refs used to be declared in <script setup>, so every visit to PlayPage made
FRESH refs (leaving + returning reset them). Now they are module singletons, so
plain ref() values KEEP their value across in-page navigation. A full page
RELOAD still resets them (module re-evaluates); only localStorage-backed refs
survive a reload. => The change only affects plain ref() values, on client-side
navigation.

DEFINITIONS (so the buckets are unambiguous):
  LIGHT / STICKY SETTING = a preference or toggle the user deliberately chooses,
    where retaining it across navigation is harmless or nice and can NEVER show
    stale game data (e.g. tile size, chording mode, a chosen algorithm). Safe to
    leave persisting. (Most are already useLocalStorage.)
  TRANSIENT RUNTIME STATE = reflects one specific game's progress/result, a modal
    open/closed flag, a scratch input field, or live replay/analysis/worker
    status. Retaining it across navigation produces visually-WRONG or confusing
    UI on return. RESET these on mount.

HOW TO IMPLEMENT THE RESET (keep it co-located)
------------------------------------------------------
  Export a `resetTransientSettings()` from useSettings.js that sets every Group-A
  ref back to its initial value (and rebuilds statsObject's default shape). Call
  it from PlayPage onMounted, BEFORE game.initialise():
      onMounted(() => { resetTransientSettings(); ...existing... });
  This avoids importing ~30 refs into PlayPage just to reset them, and keeps the
  reset next to the declarations so they can't drift apart.
